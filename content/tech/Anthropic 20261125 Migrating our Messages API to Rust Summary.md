## When the test suite is not the specification

The Python implementation could not simply be frozen while the Rust version caught up. Anthropic was adding models and features throughout the migration, so the behavior to be reproduced kept moving. Nor was the test suite a complete contract. Twenty binary options already imply more than one million combinations before prompts and models vary, and an audit found more than 100 assertions that had become weaker when tests were ported.

The gap was visible in production. In April, the Rust service passed about 98% of its tests, yet only about a quarter of compared production inputs matched Python. Some differences were tiny but meaningful. Python might escape an emoji in a JSON tool call while Rust emitted it directly. Both requests would succeed, but they would send different prompts to the model. Production traffic also weighted defects by frequency, so one common edge case could dominate mismatch volume even if it appeared only once in a test suite.

Anthropic therefore treated the existing Python service as the specification. This is a form of differential testing, but an inference API breaks two assumptions common in ordinary shadow traffic. A request must not count twice toward billing or limits, and two genuine model runs can produce different answers. The system solved both problems by calling the model only once, then replaying the same token stream through the Rust output path. It compared Python and Rust at checkpoints before and after that single model call: validation, option resolution, prompt construction, output parsing, streaming, and usage accounting.

Checkpointing made the first divergent stage visible. To protect privacy, the comparison system did not expose customer prompts or replies. Instead, it recorded a fingerprint describing where a difference occurred, which fields differed, and the size or shape of the difference. The charted input-match rate began at 24% and ended at 99.6%, after falling to 6.5%. Anthropic notes that the comparison population changed over time and excludes six misleading days.

## Three verification loops

Every mismatch generated a record, but a single bug could generate hundreds of thousands of nearly identical records. A job ran every 10 to 30 minutes, grouped records by the fields that differed, and alerted a coordinating Claude agent only when a new kind appeared. The coordinator assigned a worker agent and opened a Slack thread where engineers could inspect the diagnosis and steer the work.

The fast inner loop ran in an isolated workspace containing both codebases. Given only a fingerprint, an agent formed a hypothesis and wrote its own synthetic request or model reply to trigger the same difference. The input check compared prompt construction without calling a model and ran in under a second. A later output check fed both services a scripted reply from a fake model. Once the agent reproduced the mismatch, it edited the Rust implementation until the outputs matched and added a regression test.

The production outer loop tested whether an approved fix actually removed the fingerprint from shadow traffic. Engineers reviewed a pull request before deployment, then agents compared comparable requests across builds using non-content metadata such as the selected model and whether a request used tools, prompt caching, or extended thinking. If the mismatch remained, the work returned to the inner loop with new evidence. This slower loop caught hypotheses that happened to fit an agent’s synthetic example but not the real distribution.

The memory loop generalized lessons from individual fixes. Engineer corrections became written rules available to later agents, searches for similar mistakes elsewhere, lints, and permanent checks. After an engineer told one agent to reproduce Python’s actual behavior rather than guess, another agent used that rule to find seven more speculative ports. A daily check eventually flagged Python changes that might need a corresponding Rust edit, while a merge check required either that update or an explicit exemption.

The three loops separated different kinds of judgment. Agents could cheaply explore inside the sandbox, engineers reviewed concrete patches at the boundary, and production traffic provided the final behavioral evidence. This placement of human review mattered because a verifier only rewards what it measures. When an agent found that the Rust service lacked a web-search tool description, it proposed copying the text into local files. The prompt matched and the local verifier passed, but an engineer rejected the patch because the real service still needed to fetch the description dynamically. Output parity had identified a symptom, not a maintainable solution.

## Verification as migration infrastructure

Anthropic gradually moved production traffic only after the two implementations converged. The completed Rust service used about 70% less CPU and more than 80% less memory per request, while median time to first token for the measured Claude Code traffic fell about 20%. The team achieved those gains without taking the API offline or stopping feature development in the Python service.

The broader lesson is that AI changes the economics of a rewrite before it changes the need for engineering discipline. When agents can generate a parallel implementation quickly, the scarce resource becomes a trustworthy definition of correctness and a signal that localizes violations. Traditional tests remain valuable, but live behavior may be the only complete specification for a mature production service.

Anthropic’s design makes that idea operational: run the nondeterministic component once, compare deterministic stages around it, expose privacy-preserving fingerprints, and give agents a fast place to turn those fingerprints into reproducible cases. Then require review before a patch reaches a slower production loop, and convert repeated corrections into shared rules and automated checks. The durable accomplishment was not merely translating Python into Rust. It was building a verification system strong enough to let agents keep two evolving implementations in step until the replacement could be trusted.
