[OpenAI Engineering published “Inside the Codex sandbox”](https://openai.com/index/inside-the-codex-sandbox/) on November 18, 2026. The post explains how Codex constrains commands without moving them out of a developer's working environment. Its central design choice is to express one portable policy for filesystem and network access, then translate that policy into the native isolation mechanisms of macOS, Linux, and Windows.

That is a harder problem than putting an agent in a container. A container is a clean security boundary, but it can also separate the agent from the exact SDKs, tools, simulators, caches, and configuration that make a local development environment useful. An iOS workflow, for example, needs the host's Apple toolchain and simulator. OpenAI chose native process isolation so commands can use those resources while the operating system still enforces explicit limits.

## A useful sandbox starts with an honest boundary

The built-in workspace profile gives commands write access inside the project while keeping sensitive control surfaces such as `.git`, `.codex`, `.agents`, and `.aws` read-only. It allows broad reads because compilers and build systems routinely depend on files outside the repository, but disables network access by default. That combination lets an agent build and edit a project while making direct data exfiltration harder.

OpenAI is explicit that this is containment, not a proof of safety. Broad reads may expose credentials in configuration files. Write access can also create indirect execution paths: malicious code inserted into an ignored dependency might run later when an editor invokes it outside the sandbox. Training and alignment still matter because the sandbox only reduces what a command can reach and how far a mistake can spread.

Permission profiles make the boundary configurable rather than binary. A profile can inherit from a built-in baseline, grant `read`, `write`, or `deny` access to particular paths, and apply rules relative to every workspace root. Network access can be disabled, unrestricted, or routed through a proxy with exact and wildcard domain rules. Explicit deny rules take precedence over allows.

The model may request extra access for one command, but it does not grant that access to itself. The harness evaluates the request against the user's settings, either asking for approval or sending it through automated review. Enterprises can add managed requirements that restrict which profiles users may select, while layered configuration still lets individual projects narrow access further. This separation between requested capability and enforced policy is the core control point.

## Policy is shared, enforcement is native

The harness exposes a common operation: launch a command, its environment, and its process tree under a permission profile. Descendants inherit the restrictions, including processes that outlive the shell command that started them. The same primitive powers Codex's shell and file tools, and the standalone `codex sandbox` command makes it reusable outside an agent session.

Network policy is split between operating-system isolation and a shared proxy. Sandboxed processes receive HTTP, HTTPS, SOCKS, and application-specific proxy variables. The operating system blocks direct external connections, so software that ignores those variables cannot simply bypass the policy. The proxy checks the requested hostname against the profile before resolving it, which matters because even a DNS query can leak information encoded in a hostname. An unmatched domain can pause while the harness seeks approval.

This shared policy layer keeps the user-facing model consistent, but the mechanisms underneath it differ substantially:

- On macOS, Codex generates a Seatbelt policy and invokes Apple's `sandbox-exec`. The base policy denies access by default, then adds path rules and permits outbound connections only to the local proxy ports. Seatbelt is kernel-enforced and widely used, but its Sandbox Profile Language is undocumented for third parties and `sandbox-exec` is officially deprecated. Codex therefore depends on a capable but awkward platform interface.

- On Linux, Codex combines Bubblewrap and seccomp-BPF. Bubblewrap creates a mount namespace whose filesystem view reflects read-only, writable, and denied paths. A launcher then installs dynamically compiled syscall filters, sets `no_new_privs`, and executes the command so descendants cannot gain privilege through setuid programs. For restricted networking, each sandbox gets its own network namespace and loopback listener. A process outside that namespace relays approved traffic to the shared proxy without exposing the host network namespace to the command.

- On Windows, Codex is moving from an ACL-, firewall-, and sandbox-user-based design to Microsoft's MXC library. MXC uses native process isolation and accepts a structured execution request covering the command, filesystem, network, desktop, and clipboard. Codex preserves compatibility by allowing registry reads and the Win32k and desktop access needed for PowerShell startup, while disabling clipboard access, input injection, desktop controls, and system-setting changes. It also prevents MXC from falling back to changing host filesystem permissions, avoiding persistent security state after the command exits.

The Windows translation exposes an important general lesson: policy languages have edge cases. More-specific paths can override broad drive grants, and aliases to the same path receive the stricter permission. But MXC accepts concrete deny paths rather than globs, so Codex expands deny patterns before launch; a new matching file created during execution is not automatically covered. Its proxy arrangement also permits host loopback, which means other local services remain reachable. A portable abstraction still needs platform-specific threat analysis.

## The sandbox is also a building block

The post demonstrates using `codex sandbox` to constrain an MCP server that would otherwise start as an unrestricted `npx` process. The server's package is cached in advance, network access is disabled at runtime, and writes are limited to the package cache and one data directory. This is a practical example of turning the agent's own isolation layer into a general least-privilege wrapper for tools the agent calls.

The broader engineering takeaway is not that one sandbox mechanism wins everywhere. It is that a usable agent boundary needs three layers: a policy people can understand, a harness that mediates escalation, and native enforcement that survives uncooperative child processes. OpenAI keeps the first two consistent while accepting different low-level implementations on each operating system. That approach preserves the developer's real environment, but it also forces the system to state its tradeoffs clearly. Sandboxing makes powerful local agents safer by bounding their authority, not by pretending their environment is simple or risk-free.
