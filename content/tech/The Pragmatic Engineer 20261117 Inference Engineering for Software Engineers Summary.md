[The Pragmatic Engineer surfaced its November 17 deep dive, “Inference engineering for software engineers.”](https://newsletter.pragmaticengineer.com/p/inference-engineering-for-software-engineers) The article reframes model serving as a normal production-systems problem. Once an AI feature has real traffic, choosing a model is only the first decision; teams must also manage cost per completed task, tail latency, cache locality, capacity, failure recovery, and the point at which shared infrastructure should give way to dedicated GPUs.

## Start with the workload, not the leaderboard

Most teams begin with a frontier lab because its API offers the quickest route from an experiment to a working product. Open-weight models become attractive after usage grows: The Pragmatic Engineer cites reported per-token savings of about 50 percent at Uber, 90 percent at Pinterest, and 56 percent at AT&T. The important qualification is that a cheaper token does not necessarily produce a cheaper result. Models use different numbers of tokens, take different paths through an agent loop, and fail in different ways, so cost should be measured per successful task.

This makes a private evaluation set the central asset in a migration. Public benchmarks can narrow the field, but they rarely match a product's prompts, tools, context lengths, latency budget, or definition of an acceptable answer. A team should replay representative production traces against candidate models, measure task quality and total cost, and use an A/B test when it lacks a mature eval suite. The goal is not to identify the universally best model. It is to find the least expensive model that remains good enough for a particular class of work.

That logic also supports routing rather than a one-time model replacement. Simple requests can go to a cheaper model while difficult ones stay on a frontier system. An OpenAI- or Anthropic-compatible endpoint makes the mechanical switch look easy, but interface compatibility does not guarantee equivalent behavior. Providers can change context limits, quantization, temperature defaults, and other serving choices. The article cites endpoint-accuracy scores for the same open model ranging from 93 to 102 percent of a reference deployment, with statistical uncertainty around those measurements. The model name alone therefore does not specify the service a customer actually receives.

## The usual migration has three stages

The article describes a progression that follows product maturity:

1. Use a frontier lab's multi-tenant API.
2. Move suitable traffic to an open model hosted by an inference provider's shared API.
3. Rent dedicated GPUs when scale, predictability, or customization justifies the commitment.

The middle stage preserves the operational convenience of an API while reducing model cost. It also preserves many of the weaknesses of shared infrastructure. Customers compete for the same replicas, have little control over placement, and may encounter rate limits or inconsistent latency. A provider can add capacity, but bringing a new model replica online is not instantaneous. The article suggests that rate-limit pressure, unstable performance, and sustained high spend are signals that a workload may have outgrown this stage.

Dedicated capacity gives the customer more control over latency, model availability, and post-training. A company can keep a chosen model version running instead of accepting a vendor's replacement schedule, and it can post-train a smaller model for a specialized task or fine-tune for niche domains with non-public data. Modal told the authors that roughly 10 percent of its customers pursue this degree of customization, which indicates that it is an advanced option rather than the default.

Control comes with a larger bill and more infrastructure responsibility. Scarce GPU supply can require long commitments, and inference providers themselves may span several clouds or operate bare metal to find enough capacity. A dedicated deployment also forces decisions about model size, interactive latency versus batch throughput, cache memory, failover, and utilization. This is why the article treats dedicated capacity as a late stage for mature, large-scale products rather than the default.

## Tail latency and cache behavior reveal the real system

Time to first token is the first production metric the article examines closely. Median latency is insufficient because multi-tenant inference has a long tail: some requests wait behind heavier neighbors, some trigger a cold replica, and others land where their prior context is not cached. Engineers need p95 and p99 measurements from the client as well as provider-side inference timing. The user's wait includes network transport and connection setup, so techniques such as connection pooling can matter even when the model server itself is fast.

The key-value cache is where the supposedly stateless API meets the stateful nature of conversations and agents. A model must process the prompt before it can generate a response, but repeated prefixes can reuse cached attention state. Providers try to keep related requests on replicas with the right cache. When that locality fails, the cache may need to be loaded or the prompt recomputed, increasing both latency and cost. Applications should therefore observe prompt-cache utilization and structure stable instructions and context so reusable prefixes remain reusable.

This is also why dedicated GPUs are not automatically efficient. A team must size cache memory against model weights and concurrency, balance interactive latency against batch throughput, and plan failover. Speculative decoding can use spare compute to draft tokens for the main model to verify, but it is another workload-dependent optimization, not a universal switch.

## The evidence points to a method, not a guaranteed saving

The article draws on interviews with Modal, Fireworks AI, and Baseten, all of which sell infrastructure discussed in the piece. The authors disclose that the publication has no affiliation with the vendors, but many operational claims still come from providers rather than a neutral, cross-vendor benchmark. The cited corporate savings are useful signals, not promises that another workload will reproduce them.

The durable lesson is a sequence of measurement. Establish task-level evals, route only the work a cheaper model can handle, observe client-side latency and cache behavior, and graduate to dedicated capacity only when the traffic can keep it busy or the product needs tighter control. Moving away from a frontier API is not primarily a procurement decision. It is the point at which model choice becomes distributed-systems engineering.
