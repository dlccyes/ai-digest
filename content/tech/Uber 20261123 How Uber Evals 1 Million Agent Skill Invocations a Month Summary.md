[Uber Engineering published “How Uber Evals 1 Million Agent Skill Invocations a Month”](https://www.uber.com/us/en/blog/optimizing-ubers-agent-skills/) on November 23, 2026. The post describes the infrastructure Uber built after its internal agent-skill marketplace grew from one skill to more than 5,000 in a year and usage exceeded one million invocations in a month. Its central lesson is that a skill stops being “just a prompt” at enterprise scale. It becomes a versioned software component that needs ownership, distribution, telemetry, evaluation, cost controls, and a retirement path.

Uber defines a skill as a directory centered on a `SKILL.md` file, with optional scripts and references. The format is deliberately progressive: an agent initially sees only a short name and description, loads the instructions when it selects the skill, and reads supporting material only when a step needs it. This lets thousands of workflows remain discoverable without filling every agent session with thousands of instructions.

## Treating workflows as a shared platform

The marketplace is a Git repository, so the mechanisms already used for software ownership also govern skills: reviews, history, and named maintainers. Uber divides the catalog into three tiers. Domain skills can be published by a team after a peer review and CI check. Core skills receive centralized review and maintenance because they serve many groups. Roughly 100 always-on skills cover common work such as pull requests, code review, data analysis, and tool access.

That hierarchy solves only the catalog problem. Engineers also use several agent harnesses, each with different configuration and installation conventions. Uber's `aifx` command-line interface normalizes those differences. It installs skills or larger plugins, manages identity and MCP access, and merges six configuration layers, from company defaults down to local overrides. A repository can therefore declare the workflows it needs while an engineer can switch among Claude Code, Codex, OpenCode, and Uber's own systems without rebuilding the same environment by hand.

Discovery is treated as a ranking problem rather than a documentation problem. A `find-skills` workflow queries a catalog that combines classification, evaluation results, and actual use. Uber's internal context graph can also recommend workflows used by a person's peers. The important design choice is that popularity is only one signal. A frequently invoked skill can still be expensive, unreliable, or obsolete.

## Evaluation must cover the path, not only the answer

Uber instruments agents through OpenTelemetry hooks. A usage event records the skill and version, whether the agent or user selected it, and operational context, but not prompt text or file contents. The platform derives 12 measures for each skill, including reach, retention, cost, latency, errors, versions, tools, and agent surfaces. Authors inspect those signals in Skill Workshop, the web application and plugin used to develop and maintain skills.

Each skill begins with a specification of its goal, required output, permitted or forbidden tool actions, and supported agents and models. Skill Workshop compiles the instructions and test prompts from that specification, then regenerates them when the underlying model or harness changes. Uber also runs a linter for mechanical failure patterns. For example, a step should have one objective, a concrete command, a result check, and explicit recovery instructions rather than a vague suggestion to retry.

The evaluation suite is intentionally mixed. Uber recommends about 5% fixed golden cases with mocked tools, 80% real prompts scored on the agent's trajectory, and 15% cases judged by the author. Tests run on a background-agent platform, a managed sandbox, and remote development machines. The clean environments expose hidden dependencies on an author's laptop, such as cached files, particular paths, or operating-system utilities.

This setup reflects the limits of deterministic pass rates for nondeterministic systems. Uber found that an evaluation passing 70% to 90% of runs can be more informative than one passing 100%, because perfect consistency may indicate that the test is insensitive to meaningful changes. Human-annotated examples help calibrate model judges. Outcome scoring is paired with trajectory scoring, which asks whether the agent used the intended tools, retrieved the right evidence, and followed the required recovery path.

Uber also uses ablation rather than assuming that instructions help. It replays real prompts with and without a skill, or with parts of the skill removed, and asks a blind judge to choose the stronger result. In one warehouse-query workflow, removing the skill caused 13% more tool calls, six times as many tool errors, and 31% longer execution; the version with the skill won 87% of comparisons. The ablation process also tests whether a skill still adds value as models improve, since some skills may need to change or retire.

## Quality and cost share the same feedback loop

Because a skill adds instructions and tool results to the running context, its cost persists beyond the invocation itself. Uber estimates per-invocation cost by subtracting the session's cumulative cost immediately before and after a skill call, then compares that measure across versions. The number is not a perfect attribution, since it includes related calls in the same interval, but it is useful for finding expensive workflows and measuring changes.

Several optimizations move deterministic work away from the main model context. A skill can delegate a bounded task to a cheaper worker model, returning only a compact result; this cut one tracing workflow's cost by 46%. A required script can run as the skill loads, saving a model turn; one search workflow fell from four turns to three and reduced mean cost by 32%. Pull-request polling can run in a background agent on a cheaper model rather than repeatedly consuming the primary session.

Uber's largest architectural change is Code Mode. Instead of installing more than 100 MCP tools and placing 50,000 to 70,000 tokens of tool descriptions into every prompt, utility scripts call tools through `aifx` and a gateway, write large results to files, and let the agent inspect only what it needs. Uber estimates that one 50-row query required about 1.4 million context tokens with an installed tool server versus roughly 900 with Code Mode. The scripts become reusable packages, giving many skills one tested implementation of common operations.

The final loop lets agents report their own operational friction. An always-available `log-papercut` skill records what the agent attempted, what it expected, what happened, and a possible fix. Reports are grouped by skill, triaged, converted into regression cases, and measured after deployment. In three months, agents filed thousands of these reports, exposing defects such as shared temporary files corrupting concurrent pull requests, seconds being passed where an API expected milliseconds, and a monitor retrying a permanent 404 until timeout. Human acceptance signals, including comments on agent-created pull requests, feed the same evaluation sets.

The broader engineering takeaway is that reusable agent instructions need the same discipline as production software, but their tests must account for changing models and probabilistic behavior. Uber's system combines stable specifications with empirical evaluation of both outcomes and execution paths. It also measures whether a workflow remains worth its context and latency costs. At scale, the durable asset is not the prose in `SKILL.md`; it is the lifecycle around that prose, from discovery and controlled rollout to evidence-based simplification and retirement.
