Rubicon's central scaling problem is not storing more code. It is deciding which tiny pieces of mutable state must be ordered while thousands of writers create immutable data around them. GitHub's official Engineering blog explains that distinction in [“Inside GitHub’s new Git storage architecture”](https://github.blog/engineering/architecture-optimization/inside-githubs-new-git-storage-architecture/), a detailed look at Project Rubicon, the platform the company is building for repositories worked on by large fleets of software agents.

GitHub says its busiest repositories currently see at most dozens of writes per second, usually in bursts. Agents change that traffic shape: they can run continuously, push in parallel, and trigger additional reads from CI, deployments, and other agents. Rubicon therefore targets thousands of writes per second to one repository while allowing read capacity, write capacity, and maintenance work to scale independently. In internal tests, GitHub reports that one repository supported 5,000 concurrent agents and 7,200 pushes per second while continuing to serve low-latency reads. Those are GitHub's internal results, and the architecture remains in limited private preview, but they reveal the scale the design is intended to reach.

## Separate what must agree from what need not

The central insight comes from Git's data model. Commits, trees, and file contents are immutable objects named by cryptographic hashes. Multiple writers can upload those objects concurrently without coordinating because identical content has the same name and different content has a different one. References such as branch heads are different: they are small, mutable pointers, and competing updates must be ordered so that one writer cannot silently overwrite another.

Rubicon turns that distinction into a system boundary. Git object packs and read-acceleration data live in Azure Blob Storage. References and the manifest listing a repository's packs live in Ref-CAS, a replicated log service built around reference compare-and-swap operations. Disposable “virtual replicas” serve reads and writes, using local disk only as a rebuildable cache. A separate fleet performs pack compaction and garbage collection directly against durable storage.

A push first reaches a virtual replica, which indexes the incoming pack, checks object connectivity, and uploads the pack to Blob Storage. Only after those objects are durable does the replica submit a Ref-CAS transaction that adds the pack to the manifest and updates the affected references. A read checks its cached repository version against Ref-CAS; if nothing has changed, the check returns without transferring the reference set. If the replica is behind, it receives the current references plus pointers to the pack data it needs.

This order matters. Ref-CAS never has to replicate or validate large object packs, yet a committed reference can never point to data that has not reached durable storage. Correctness is concentrated in a small ordered state, while bulk data follows a path optimized for capacity and aggregate throughput.

## Why object storage alone was not enough

GitHub tried keeping reference state in Blob Storage before building Ref-CAS. A single write-ahead-log blob made reads cheap, but its conditional writes serialized every update and limited throughput to the mid-hundreds per second. Splitting references across several blobs allowed unrelated writes to proceed in parallel, but every read then had to check every segment and wait for the slowest one. That was a poor exchange because reads outnumber writes by orders of magnitude.

Ref-CAS preserves cheap version checks without making all references share one lock. Each transaction locks only the references it touches, verifies their expected values, and becomes visible after a majority of log replicas record it. Agents usually push to separate branches, so their transactions can replicate in parallel; only writers racing on the same reference contend. Every committed transaction receives a log sequence number that also acts as the repository version. GitHub says the service can process reference-state transactions at tens of thousands of operations per second.

The broader lesson is that consensus should cover the smallest state whose ordering establishes correctness. Putting immutable objects inside the same quorum would make every participant process large payloads. Removing consensus entirely would make branch updates unsafe. Ref-CAS is the narrow coordination point between those extremes.

## Move maintenance off the request path

Thousands of pushes create another problem: every push adds a pack, and reads become more expensive as pack counts grow. GitHub's older architecture ran compaction on the same replicas that served traffic, repeating the work on every replica and making request capacity compete with maintenance.

Rubicon assigns compaction to dedicated workers. A worker leases one shard of a repository's packs, accumulates new packs into a segment, seals the segment when it reaches a size, age, or count threshold, and merges it into fewer, larger packs. Before publishing the result, it verifies that the output contains exactly the same objects as the inputs. One Ref-CAS transaction adds the replacement packs to the manifest; a second removes the old packs, which are deleted later. Hash-based sharding lets GitHub add workers and compaction throughput independently, while tiered merging keeps the pack count roughly flat as pushes increase.

Virtual replicas are similarly independent. GitHub can add them when a repository gets busy, route traffic to warm caches when possible, and replace any failed replica without recovering authoritative local state. Correctness depends on Blob Storage and Ref-CAS, not on a particular server receiving the next request.

## The engineering takeaway

Rubicon is a strong example of designing around semantic properties instead of treating an existing server as an indivisible unit. Git already separates immutable content from mutable names; GitHub uses that property to split storage, coordination, serving, and maintenance into components with different scaling rules.

The architecture also shows why “stateless compute” is incomplete as a design slogan. The virtual replicas are disposable only because durable state has been carefully divided, update order has been made explicit, cache freshness has a cheap version protocol, and background rewriting has transactional publication rules. Decoupling works when the contracts between components preserve the old system's invariants.

GitHub plans to extend the design with partial replicas, object-level reads, materialized views, global replicas, clone-free agent access, atomic commit APIs, and event streams. Whether agent traffic reaches the projected scale remains uncertain, and the published throughput figures are GitHub's own internal results. Even so, the mechanism is broadly useful: when a workload appears to require global coordination, first ask which bytes truly need agreement. Shrinking that set can turn a monolithic scaling limit into several independently solvable problems.
