[The Pragmatic Engineer surfaced Railway's incident report](https://newsletter.pragmaticengineer.com/p/the-pulse-what-can-we-learn-from-114) in its November 12 Pulse. The original source is Railway's November 10 postmortem, [“Incident Report: October 21st Security Attack.”](https://blog.railway.com/p/incident-report-october-security-incident) It is a useful account of what changes when an attacker can search a stolen codebase and test many escalation paths at agent speed: a flaw that initially exposed files on one build host became the first link in a chain reaching customer secrets.

## One narrow credential became a platform credential

The attacker began probing Railway's multi-tenant build system on October 20. At 07:28 UTC, they used a previously unknown vulnerability to partially escape a build's filesystem isolation and read files on the host virtual machine. That exposed a credential intended to let builders perform limited work such as pushing completed container images.

The credential's effective authority was much broader. Railway's self-hosted Temporal cluster accepted it as a trusted client, allowing the attacker to read stored histories from 353 other builds. Those histories could contain environment variables, secrets, and repository-scoped GitHub tokens. The same credential could fetch cached repository snapshots; one snapshot held Railway's internal monorepo because Railway deployed its own support service through the build system.

Possession of the monorepo changed the attack from blind probing to source-assisted discovery. Railway inferred that the attacker had the code when they began testing endpoints that had not been in use for weeks, months, or years and had no live references within Railway's system. After Railway revoked the original build credential, the attacker found an erroneously configured OpenID Connect binding in the company's deployment system. At 03:26 UTC on October 21, that binding yielded a short-lived cloud credential.

The cloud credential opened a path to an SSH key and another credential used inside Railway's production network. The SSH key reached an orchestration machine whose disk held a credential capable of asking the cloud key-management service to decrypt per-environment data keys. The platform's envelope encryption limited the blast radius—each environment had its own data key—but the runtime still needed a legitimate decryption path to start customer workloads. The attacker assembled the same components the platform used in normal operation.

## The target was usable AI access

Database logs show that the attacker queried encrypted variables whose names matched regular expressions for AI-provider keys, prioritizing environments with many variables. They retrieved encrypted envelopes from 04:07 to 05:21 UTC and used Railway's decryption path during two windows between 04:42 and 07:15. Railway disabled active cloud credentials and the decryption service at 07:14, shut down parts of the platform, and says the attacker had no customer-data access after 09:25.

Railway can identify environments touched by the queries, but not every variable decrypted. Its estimate that at most 1.85 percent of workspaces—about 100,000—could have had a variable exposed is therefore an upper bound, not a count of confirmed stolen secrets. The exposed data also included bring-your-own-key agent credentials and GitHub OAuth tokens for 1,852 users. Railway reset those tokens and says it found no resulting Railway-account logins. It reports no evidence that customer repositories or databases were accessed, although one attacker query also matched cloud, database, and payment-service credentials.

Unauthorized use of stolen keys was estimated at about \\$740,000, across workloads ranging from coding agents to AI-training pipelines. Railway believes the keys moved through relay or resale services and may have supported model distillation, but it does not establish that the original intruder operated those services or identify the attacker. It also says the attacker used safeguard-removed, or “abliterated,” models and a harness resembling ARTEX; that characterization is based on Railway's investigation and context from Wiz, not a released forensic transcript that independently proves which models or tools ran the attack.

This distinction matters. The postmortem documents an attacker moving quickly and in parallel, but the decisive failures were familiar security failures: shared infrastructure, a credential trusted outside its intended role, source snapshots reachable from a build system, an incorrect identity binding, an accessible SSH key, and a production machine holding decryption authority. On Railway's account, AI increased the speed at which those weaknesses could be composed; it did not create the trust relationships.

## Recovery required replacing trust, not just patching a bug

Railway did not treat the first isolation fix as sufficient. Within an hour, its own hardening team derived a second exploit by modifying the original vector. The company accelerated a planned migration so every build now runs in a dedicated ephemeral virtual machine, while each build credential can push only one specific image. It rebuilt affected systems from validated source, rotated internal credentials, created new public-key infrastructure and a root certificate authority, disabled and then manually restored CI-dependent services, and invalidated every user session and token.

The response imposed real availability costs. Builds were halted twice, and customers who rotated a secret sometimes could not redeploy until the new build fleet was ready. Existing deployments continued running, but revoked credentials could still make applications fail. Credential rotations drove build volume to nearly two orders of magnitude above baseline, while the storage-architecture switch raised upstream storage bandwidth by at least tenfold. Railway restored all build plans by late October 22, while support and other features took longer.

The durable engineering lesson is to evaluate credentials by where every accepting service will honor them, not by the purpose printed on their label. Build isolation, workload identity, cache access, CI credentials, network reachability, and secret decryption form one security system. If a compromised component can combine them, encryption at rest may only delay exposure. Agent-speed attackers make stale endpoints and overly broad machine identities especially expensive because they can search and test the whole graph faster than defenders can reason about it manually.

Railway says every exploited weakness has been closed, but the investigation and law-enforcement work remain open, and indicators of compromise had not yet been published with the report. Its postmortem is therefore strongest as an architectural reconstruction and a record of the response—not as final attribution of the attacker, the tooling, or every downstream use of the stolen keys.
